# 웹 미리보기 진단

확인일: 2026년 10월 22일 (한국 시간)

## 결론과 확인 범위

사용자가 제공한 전체 캡처에는 왼쪽 위에 `Index`가 표시됩니다. 실행 중인 Vite 서버와 HTML 파일 시각화를 구분해야 하며, 일반 서버에서 정상 동작한다는 사실만으로 파일 미리보기 호환성을 판단할 수 없습니다.

추가 실험에서 두 가지를 재현했습니다.

1. 개발용 `index.html`만 프레임에 삽입하면 `/src/main.tsx`를 불러오지 못해 앱이 렌더링되지 않습니다. 이 파일은 Vite 서버를 통해 실행해야 합니다.
2. `allow-forms`가 없는 제한된 프레임에서는 기본 폼 제출이 차단되어 생성·업로드·프로필 저장 버튼이 동작하지 않았습니다. 해당 버튼이 먼저 React의 로컬 처리 함수를 호출하고 기본 제출을 취소하도록 보완했습니다. 서버 제출이나 외부 요청을 추가하지 않았고 프레임 보안 정책도 변경하지 않았습니다.

JS·CSS·폰트·이미지를 모두 포함한 단일 HTML을 `sandbox="allow-scripts allow-downloads"` 프레임에서 검증했습니다. 저장소 접근과 기본 폼 제출이 차단된 상태에서도 5개 화면, 데모 생성, 업로드, 프로필 편집이 통과했고 콘솔 오류 및 요청 실패는 없었습니다. 저장소 차단 시 기존 안내가 표시되며, 해당 미리보기 세션의 데이터는 새로고침하면 사라질 수 있습니다.

이 재현 환경은 실제 Codex 뷰어가 아닙니다. 캡처의 `Index`가 어떤 파일인지와 Codex 내부 로그는 확인할 수 없으므로 **사용자가 본 오류와 동일한 직접 원인이라고 확정하지 않습니다**. 이전의 플랫폼 문제 중심 설명은 위 앱·파일 미리보기 호환성 진단으로 보완합니다.

## 실제 점검

| 점검                     | 관찰 결과                                                     |
| ------------------------ | ------------------------------------------------------------- |
| 개발 서버                | `0.0.0.0:5173` 수신 중, HTTP 200                              |
| 프로덕션 미리보기        | `0.0.0.0:4173` 수신 중, HTTP 200                              |
| React 화면               | 두 서버에서 5개 화면의 제목·이미지·폰트 표시 확인             |
| 생성 흐름                | 두 서버에서 키워드 입력 후 데모 결과 표시 성공                |
| 브라우저 콘솔 error      | 0건                                                           |
| JavaScript pageerror     | 0건                                                           |
| 요청 실패 / HTTP 4xx·5xx | 0건                                                           |
| 개발 서버 WebSocket 오류 | 0건                                                           |
| 응답의 iframe 차단 헤더  | X-Frame-Options 및 CSP frame-ancestors 없음                   |
| 공개 미리보기 URL        | 현재 도구에 포트 공개·호스팅·터널 기능이 없으며 발급하지 않음 |

이 결과는 클라우드에서 실행한 Chromium에 관한 것입니다. 사용자의 Codex 웹 미리보기에서 수집한 로그가 아닙니다. 이전 의존성 재설치 후의 Vite 캐시 문제는 이미 서버 재시작으로 해결됐으며, 이번 점검에서는 재현되지 않았습니다.

## 변경 사항

새 앱 기능이나 생성·분석 API는 추가하지 않았습니다. 디자인은 유지하고, 확인된 프레임 호환성 문제와 별도 실행 경로만 보완했습니다.

- `src/App.tsx`: 생성·업로드·프로필 저장의 로컬 처리 함수를 버튼 클릭에서 먼저 실행하여 기본 폼 제출에 대한 의존을 제거.
- `scripts/verify-inline-preview.mjs`: 저장소 및 기본 폼 제출이 차단된 프레임에서 동작 검증.
- `npm run test:inline-preview`: 위 프레임 검증 명령. 일반 E2E 6개도 다시 통과.

- `scripts/build-portable.mjs`: 프로덕션 JS·CSS·폰트·데모 이미지를 단일 HTML에 포함.
- `scripts/verify-portable.mjs`: Vite 없이 그 HTML만 제공하는 독립 서버를 띄워 실제 브라우저 테스트. 외부 HTTP 요청 차단.
- `npm run build:portable`, `npm run test:portable`: 배포본 생성·검증 명령.
- 생성물 `portable/`은 Git 및 포맷 검사에서 제외.

## 별도 실행본 검증

단일 HTML을 실제 Chromium에서 실행하여 다음을 확인했습니다.

1. 초기 화면·이미지·폰트 렌더링.
2. 데모 생성과 800×800 PNG 다운로드.
3. 새로고침 후 히스토리 유지.
4. 이미지 업로드, 승인 대기와 명시적인 로컬 승인.
5. 프로필 편집 후 스타일 화면에 반영.
6. 모바일에서 5개 화면 탐색, 가로 넘침 없음.

콘솔 오류·런타임 오류·외부 네트워크 요청은 0건입니다. 결과 JSON은 `portable/verification/report.json`에 생성됩니다.

관리형 클라우드 Chromium에서 `file://`를 직접 열면 `ERR_BLOCKED_BY_ADMINISTRATOR`가 발생합니다. 해당 관리자 정책을 변경하거나 우회하지 않았습니다. 단일 HTML은 허용된 로컬 HTTP 서버에서 검증했으며 **파일 더블클릭 실행은 이 환경에서 미검증**입니다. 이 정책 오류가 사용자의 Codex 오른쪽 뷰어 오류와 같은 원인이라는 증거는 없습니다.

## 사용자가 실제 앱을 확인하는 방법

현재 우선 확인할 파일은 `/workspace/review/Brand-Asset-AI-Studio-Preview.html`입니다. 개발용 `Index` 대신 이 단일 HTML을 선택하여 엽니다. 별도 터미널이나 외부 서버 없이 실행할 수 있도록 의존성을 포함했습니다. Codex 뷰어가 이 파일을 실제로 표시하는지는 사용자 쪽 확인이 필요합니다.

로컬 서버·ZIP 방식은 사용자 요구에 맞지 않으므로 우선 안내하지 않습니다. 기존 대안의 실행 스크립트는 남겨 두었습니다. 공개 호스팅 URL은 발급하지 않았습니다.
